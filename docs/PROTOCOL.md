# Protocol — the raw Tuya ZCL frame

This page documents the exact frame sent to the valve, how the converter builds it, and
how to adapt the code if a future zigbee-herdsman version changes its API.

## The frame

The timer is controlled by a **cluster-specific ZCL frame** on the Tuya proprietary
cluster `0xE001`, command `0xFE`:

| Byte(s) | Value | Meaning |
|---|---|---|
| 0 | `0x11` | Frame control. Bit field: frame type = cluster-specific (`0b01`), manufacturer-specific = **no** (`0`), direction = client→server (`0`), disable default response = **yes** (`1`) |
| 1 | `0xNN` | Transaction sequence number (arbitrary, generated by the stack) |
| 2 | `0xFE` | Command ID (Tuya timer command) |
| 3 | `0x0B` | Sub-command: “set timer value” |
| 4-7 | `UInt32BE(seconds)` | Timer in seconds, **big-endian** |

Example frames (after the sequence byte):

| Duration | Seconds | Payload |
|---|---|---|
| 1 min | 60 | `FE 0B 00 00 00 3C` |
| 5 min | 300 | `FE 0B 00 00 01 2C` |
| 10 min (default) | 600 | `FE 0B 00 00 02 58` |
| 30 min | 1800 | `FE 0B 00 00 07 08` |
| 1 hour | 3600 | `FE 0B 00 00 0E 10` |
| 2 hours | 7200 | `FE 0B 00 00 1C 20` |
| 3 hours | 10800 | `FE 0B 00 00 2A 30` |

Sources:

* Sniffer capture published in zigbee2mqtt issue
  [#28589](https://github.com/Koenkk/zigbee2mqtt/issues/28589): payload
  `11 0C FE 0B 00 00 00 3C` for a 60 s countdown (byte `0C` is the sequence number).
* [`fergus3000/tuya-ts0049-timer-fix`](https://github.com/fergus3000/tuya-ts0049-timer-fix)
  which sets the timer with a raw send from a ConBee/deCONZ setup, and reports the value
  persists on the device.

Important properties:

* The frame is **not manufacturer-specific** (no manufacturer code on the wire). The
  built-in `genOnOff` cluster of the device is used for normal on/off, but the timer must go
  through `0xE001`.
* `disableDefaultResponse` is set: the device does not acknowledge the frame. Success is
  proven by the new behaviour (the valve closes at the new time), not by a response.
* The value is stored in the valve firmware and survives re-pairing / factory reset
  (community reports). It can be overwritten at any time by sending the frame again.

## How the converter builds it (zigbee-herdsman)

zigbee-herdsman validates cluster/command names against its ZCL catalog, so `0xE001` /
`0xFE` cannot be used by name. The converter therefore declares a *cluster object* and
passes it directly:

```js
const TIMER_CLUSTER = {
    name: 'arrosageTimer',
    ID: 0xE001,
    manufacturerCode: undefined,          // -> frame control 0x11 (no manufacturer code)
    attributes: {},
    commands: {
        timer: {
            name: 'timer',
            ID: 0xFE,
            parameters: [
                // one UINT8 per byte, assembled manually (big-endian!)
                {name: 'dp', type: 0x20},
                {name: 'b0', type: 0x20},
                {name: 'b1', type: 0x20},
                {name: 'b2', type: 0x20},
                {name: 'b3', type: 0x20},
            ],
        },
    },
    commandsResponse: {},
};

await endpoint.command(
    TIMER_CLUSTER, 'timer',
    {dp: 0x0b, b0: s >>> 24 & 0xff, b1: s >>> 16 & 0xff, b2: s >>> 8 & 0xff, b3: s & 0xff},
    {disableDefaultResponse: true},
);
```

Mechanism, as verified in zigbee-herdsman **10.9.2**
(`src/controller/model/endpoint.ts`):

* `Endpoint.command()` calls `zclCommand(..., Zcl.FrameType.SPECIFIC)`.
* `zclCommand()` accepts a **cluster object** as `clusterKey` and resolves the command
  either by name (from that object) or accepts an **object command** directly — the latter
  bypasses the ZCL catalog validation.
* `manufacturerCode` is taken from the cluster object. With `undefined`, the generated
  frame control is `0x11` — exactly the Tuya frame above.
* `disableDefaultResponse: true` keeps bit 4 of the frame control set.

The UInt32 is assembled from four `UINT8` parameters on purpose: a `UINT32` parameter
would be serialized little-endian by the ZCL serializer, while this device expects
big-endian.

## Alternative implementation (fallback)

If a future zigbee-herdsman version rejects the cluster-object form, the documented way to
add a cluster in an external converter is `deviceAddCustomCluster` from
`zigbee-herdsman-converters/lib/modernExtend`:

```js
const {deviceAddCustomCluster, battery, onOff} = require('zigbee-herdsman-converters/lib/modernExtend');

const definition = {
    // ...
    extend: [
        battery(),
        onOff({powerOnBehavior: false, configureReporting: true}),
        deviceAddCustomCluster('arrosageTimer', TIMER_CLUSTER), // registers the cluster on the device
    ],
    toZigbee: [{
        key: ['irrigation_timer'],
        convertSet: async (entity, key, value, meta) => {
            await meta.device.getEndpoint(1).command('arrosageTimer', 'timer', {...}, {disableDefaultResponse: true});
            // ...
        },
    }],
};
```

`deviceAddCustomCluster` exists in zigbee-herdsman-converters v26 and simply calls
`device.addCustomCluster(name, clusterDefinition)`. The cluster object above can be reused
as-is. This path was not the one used in production here (the object form was tested
end-to-end), but both mechanisms were verified in the source.

## Device notes

* The valve uses endpoint **1**.
* It is a sleepy battery end device: ZCL commands are delivered when the device polls; a few
  seconds of latency is normal. Zigbee2MQTT handles retries.
* The device also has a `genOnOff` cluster (used for on/off) and reports `onTime` /
  `offWaitTime` attributes — those are unrelated to the Tuya timer and are ignored by the
  firmware when set through the standard On/Off cluster (`on_time` payloads have no effect,
  see issue #28589).
